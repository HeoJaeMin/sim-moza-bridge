# LMU 레이싱 대시보드

`lmu-dashboard`는 기존 MOZA 브리지와 분리된 Le Mans Ultimate 전용 웹 대시보드입니다. 게임 PC에서 실행한 뒤 같은 PC의 브라우저 또는 같은 로컬 네트워크의 태블릿에서 볼 수 있습니다.

## 제공 기능

- 실제 차량 좌표를 누적해 만드는 일반적인 트랙 중심선과 전체 차량 위치
- 전체 드라이버 순위, 앞차와의 interval, 선두와의 gap, 피트 상태
- 플레이어의 현재 랩 속도, 스로틀, 브레이크, 스티어링, RPM 텔레메트리
- 활성 세션 동안 플레이어와 같은 클래스 전체 차량의 랩 trace 추적과 완료/중단 시 상세 샘플 SQLite 저장
- 드라이버와 클래스를 구분한 저장 랩 재조회
- 접촉 차량, 시점, 위치, 충격량, 판정 신뢰도 기록
- 수집 상태, 프레임 지연, snapshot의 수락·거부·중복·정지·복사 불일치와 telemetry의 수락·거부·역행·지연·급변 카운터, 현재 랩 품질
- 동일 클래스 유효 참가자의 다중 랩 기준과 구간별 코칭 분석

트랙 폭, 경계선, 피트레인 형상은 수집하지 않습니다. 처음 방문한 트랙은 차량이 주행한 좌표를 약 10m 간격으로 학습하므로 첫 랩 동안 지도가 점진적으로 완성됩니다. 이후에는 같은 트랙의 저장된 지도를 바로 불러옵니다.

## 실행

데모 데이터로 UI를 먼저 확인할 수 있습니다.

```bash
cargo run --bin lmu-dashboard -- --demo
```

Windows 게임 PC에서 LMU 공유 메모리를 읽으려면 다음처럼 실행합니다.

```powershell
cargo run --bin lmu-dashboard -- --live
```

빌드된 실행 파일을 직접 실행할 수도 있습니다.

```powershell
.\lmu-dashboard.exe --live
```

브라우저에서 `http://127.0.0.1:8787`을 엽니다. 태블릿에서 보려면 신뢰할 수 있는 로컬 네트워크에서만 모든 인터페이스에 바인딩하고, Windows 방화벽에서 해당 포트를 허용합니다. 비루프백 주소는 실수로 노출하지 않도록 `--allow-remote`가 반드시 필요합니다.

```powershell
.\lmu-dashboard.exe --live --listen 0.0.0.0:8787 --allow-remote
```

이후 태블릿에서 `http://게임-PC의-LAN-IP:8787`로 접속합니다.

## LMU 세션 코칭 준비

코칭 비교는 오버레이에 표시하지 않고 별도 Markdown과 JSON 파일로 생성합니다.

```powershell
.\lmu-dashboard.exe --live --coach-report lmu-dashboard-data\session-coaching.md
```

대시보드는 최신 LMU 세션의 동일 클래스 유효 참가자를 비교합니다. 드라이버별 베스트 2랩 중앙값과 상위 25% 집단을 계산하고, 현재 scoring의 동일 클래스 선두 드라이버가 가진 유효 랩의 대표 텔레메트리를 별도 P1 기준으로 사용합니다. 선두가 바뀌거나 드라이버가 교체됐는데 새 선두의 유효 trace가 아직 없으면 이전 선두를 대신 사용하지 않고 P1 비교를 기다립니다. 텔레메트리를 거리 기준 20개 구간으로 맞춰 P1 대비 구간별 획득·손실과 누적 차이, 순위, 백분위, 표본 수와 신뢰도를 제공합니다. 여러 랩에서 반복되는 습관과 일회성 실수도 구분합니다.

최신 세션에 유효 완주 랩이 아직 없으면 보고서는 수집 대기 상태로 생성되며, 비교 집단이 바뀌면 자동 갱신됩니다. 퀄리파잉과 레이스를 포함해 LMU가 제공하는 모든 세션 유형에 같은 분석을 적용합니다. 표본이 부족하면 가능한 비교만 표시하고 신뢰도를 낮춥니다. 트래픽, 슬립스트림, 연료와 타이어 정보가 비교에 충분하지 않은 한계 및 제외된 랩의 구조화된 품질 사유를 보고서에 명시합니다. 결과는 웹 대시보드의 `COACH` 탭과 UTF-8 Markdown/JSON 보고서에서 확인합니다.

## 텔레메트리 품질

ACR 분석과 LMU 랩은 같은 4-state 품질 모델을 사용합니다.

- `valid`: 완주·커버리지·시간·샘플 조건을 통과한 trace. 완료·공식 시간 등 랩 metadata도 유효할 때 코칭 기준으로 사용
- `partial`: 중간 수집, 미완료 또는 샘플 간격 등으로 비교 기준에 쓰기 어려운 trace
- `rejected`: 게임 invalidation, 시간 불일치나 비정상 telemetry처럼 신뢰할 수 없는 trace
- `unknown`: 품질 필드가 없던 기존 저장 기록을 잘못 `valid`로 승격하지 않기 위한 호환 상태

시작점, 종료점, 트랙 커버리지, 공식 시간 일치, 샘플레이트, 최대 간격, 추정 누락·중복, 시간/거리 역행과 비정상 속도·RPM·기어·G를 검사합니다. LMU parser는 원본 NaN/무한대를 0으로 정규화하지 않으며 capture validator가 해당 sample을 거절하고 현재 랩 사유에 반영합니다. 중간부터 수집한 랩은 공식 랩타임이 있어도 `valid`가 되지 않으며 `partial`, `rejected`, `unknown`은 P1/집단 코칭 기준에서 제외됩니다.

## 저장 위치

기본 저장 파일은 실행 디렉터리의 `lmu-dashboard-data/dashboard.sqlite3`입니다. 다른 위치를 쓰려면 `--data-dir`을 지정합니다.

```powershell
.\lmu-dashboard.exe --live --data-dir D:\LMU-Telemetry
```

활성 세션 동안 scoring에 있는 전체 차량은 클래스와 관계없이 지도와 리더보드에 표시합니다. 상세 telemetry는 매 frame 플레이어 클래스 여부를 확인하고 플레이어와 같은 클래스 차량의 lap tracker에만 넣습니다. 각 완료 랩은 차량, 드라이버, 클래스 정보가 포함된 요약과 약 20 Hz 상세 샘플로 저장하며, pause/shutdown 시 진행 중인 동일 클래스 랩은 partial trace로 flush할 수 있습니다. 다른 클래스 차량의 상세 랩 telemetry는 저장하지 않습니다.

대시보드의 `현재 랩 · 내 차 · LIVE` 그래프는 항상 플레이어 차량을 표시하며, 저장 랩 선택기에서는 같은 클래스 드라이버의 저장 랩을 구분해 다시 볼 수 있습니다. 트랙 지도와 접촉 기록도 같은 데이터베이스에 유지됩니다. 즉 UI 범위는 전체 클래스이고 상세 랩 저장·코칭 범위만 플레이어 클래스입니다.

구현된 재개 정책은 마지막 기록 후 3시간 안에 track/session signature와 세션 시간 진행이 맞는 LMU 세션을 다시 만나면 기존 세션 ID를 복원합니다. 저장된 partial 랩이 있으면 차량·드라이버·클래스, 랩 번호, 거리와 세션 시간이 모두 이어질 때만 그 랩을 계속합니다. partial 랩이 없으면 세션 시간이 정지돼 있었거나 실제 경과 시간만큼 진행됐다는 근거가 있어야 재개하며, 랩 번호 감소나 세션 시간 초기화는 새 세션으로 판정합니다. 이 범위는 현재 가정한 최장 2시간 레이스와 재시작 여유를 포함합니다. 잠깐의 빈 공유 메모리 프레임은 즉시 세션 종료로 간주하지 않습니다. 세션 시간의 0.5초 이내 흔들림은 같은 세션으로 허용하지만, 그보다 큰 실제 초기화나 track/session type 변경은 새 세션을 만들며 기존 진행 랩은 `partial`로 flush합니다. 실제 LMU의 메뉴·서버 전환 조합은 아래 Windows 절차로 별도 확인해야 합니다.

데이터베이스는 SQLite `PRAGMA user_version`을 사용해 v0 → v1 → v2 → v3 순서로 transaction 안에서 제자리 업그레이드합니다. 기존 `dashboard.sqlite3`를 삭제하거나 재생성하지 않으며, `(session, vehicle, lap)` 논리 키의 중복을 정리한 뒤 유니크 인덱스를 만듭니다. 같은 논리 랩은 완전한 기록이 기존 partial 기록을 교체할 수 있지만 반대 방향으로 덮어쓰지는 않습니다. 지원 버전보다 새로운 schema를 만나면 임의로 내리지 않고 시작을 거부합니다.

업그레이드할 때는 다음 순서를 권장합니다.

1. 같은 PC의 `LIVE` 탭에서 `종료 · 저장`을 눌러 진행 중인 랩과 저장 큐를 flush합니다.
2. 프로세스가 끝난 뒤 `lmu-dashboard-data` 또는 지정한 `--data-dir` 전체를 백업합니다. SQLite WAL/SHM 파일이 남아 있다면 함께 보관합니다.
3. 새 실행 파일을 같은 `--data-dir`로 한 번 시작합니다. 시작 시 필요한 migration이 순서대로 적용됩니다.
4. `LIVE`/`COACH` 탭에서 기존 세션과 랩을 조회합니다. `sqlite3` CLI가 있으면 `PRAGMA user_version;` 결과가 `3`인지 추가 확인할 수 있습니다.
5. 실패하면 새 binary로 반복 실행하기보다 백업을 복사한 별도 디렉터리에서 원인을 확인합니다. 자동 downgrade 기능은 없습니다.

원본 샘플과 분석 요약의 보존 기간은 독립적으로 지정할 수 있습니다. 분석 보존 기간은 원본보다 짧게 설정할 수 없습니다.

```powershell
.\lmu-dashboard.exe --live --raw-retention-days 30 --analysis-retention-days 180
```

## 수집 제어와 상태

`LIVE` 탭에서 수집을 일시정지·재개하고 정상 종료할 수 있습니다. 일시정지는 진행 중인 랩과 저장 큐를 flush하고 shared-memory reader를 닫으며, 재개하면 reader를 다시 엽니다. `종료 · 저장`은 collector 종료 뒤 진행 중인 랩과 queue flush를 마치고 프로세스를 종료합니다. 각 제어 API는 실제 상태 변경과 flush 완료 응답을 받은 뒤에만 성공을 반환하며, collector 실패는 HTTP 오류로 전달합니다. 저장 일관성이 필요할 때는 콘솔 창을 바로 닫는 대신 이 제어를 사용합니다.

`/api/live`는 게임/세션/수집 상태, 샘플레이트, 마지막 프레임 지연을 제공합니다. scoring snapshot의 거절·중복·정지·복사 불일치와 개별 telemetry sample의 거절·중복·역행·지연·급변은 서로 다른 카운터로 제공해 원인을 구분합니다. reader는 활성 scoring row와 활성 telemetry block 각각의 안정성 마커를 모두 확인하므로 어느 차량의 데이터든 복사 중 바뀐 frame은 사용하지 않습니다. `/api/health`는 서버 생존 여부를 확인합니다. 제어 API는 같은 PC의 loopback 요청과 대시보드 전용 요청 헤더를 모두 요구합니다. 서버를 LAN에 열어도 태블릿은 지도·리더보드·보고서를 볼 수 있지만 pause/resume/shutdown은 실행할 수 없습니다.

## 재생 테스트와 실게임 확인

게임 없이 합성·익명화된 `src/bin/lmu_dashboard/fixtures/session_replay.json`으로 재시작 연속성, 중간 랩 partial 처리, 정상 완주 품질과 UTF-8 왕복을 회귀 테스트합니다.

```bash
cargo test --bin lmu-dashboard
```

합성 replay와 단위 테스트는 아래 항목의 코드 회귀를 막지만 Windows/LMU 실게임 동작을 증명하지는 않습니다. 실제 게임 PC에서는 별도 데이터 디렉터리를 사용해 다음 순서로 확인해야 합니다.

1. `--live --data-dir <검증용 경로>`로 시작하고 `/api/health`, `LIVE`의 연결 상태, 마지막 프레임 지연과 수락/거부 카운터를 기록합니다.
2. 멀티클래스 practice/qualifying/race에서 전체 클래스 차량이 지도와 리더보드에 표시되는지 확인합니다.
3. 플레이어와 같은 클래스 차량 및 다른 클래스 차량이 각각 완주하도록 한 뒤, 저장 랩 선택기와 SQLite에는 같은 클래스 상세 랩만 생기는지 확인합니다.
4. 플레이어 클래스의 여러 차량에서 완주 랩을 만든 뒤 `valid/partial/rejected/unknown` 표시와 P1/집단 코칭 제외 사유를 확인합니다.
5. 주행 중 `일시정지`를 눌러 partial trace와 queue가 저장되는지 확인하고, `재개` 뒤 같은 세션에서 수집이 계속되는지 확인합니다.
6. LMU 로딩의 빈 프레임 뒤 세션이 불필요하게 분리되지 않는지, track/session type 변경 또는 실제 세션 시간 초기화 때는 새 세션 ID가 생기는지 확인합니다.
7. 레이스 도중 `종료 · 저장` 후 3시간 이내 재시작해 같은 세션 ID와 진행 랩이 복원되는지 확인합니다.
8. 검증용 DB 사본으로 위 migration 절차를 실행하고 기존 UTF-8 드라이버명, 랩, 접촉, 트랙 포인트가 유지되는지 확인합니다.

각 항목은 현재 Windows 실게임 확인 체크리스트이며, 확인 결과를 기록하기 전에는 완료된 호환성 보증으로 간주하지 않습니다.

## 접촉 판정의 한계

LMU 공유 메모리는 각 차량의 충격 이벤트를 제공하지만 상대 차량 ID를 직접 제공하지 않습니다. 대시보드는 다음 기준으로 상대를 추론합니다.

- `confirmed`: 거의 같은 시각과 위치에서 두 차량 모두 충격을 보고함
- `probable`: 한 차량만 충격을 보고했지만 충격 위치 가까이에 다른 차량이 있음
- `unresolved`: 상대 차량을 신뢰성 있게 찾지 못함. 벽이나 노면 물체 접촉일 수도 있음

따라서 이 기록은 레이스 상황 복기용이며 공식 스튜어드 판정이나 책임 판단 자료로 사용하면 안 됩니다.

## 현재 범위

이 첫 버전은 LMU의 `LMU_Data` 공유 메모리 레이아웃을 대상으로 합니다. F1 25, Assetto Corsa EVO, Assetto Corsa Rally는 동일 UI와 저장 모델을 재사용하되 각 게임 입력 어댑터를 후속으로 추가할 수 있습니다.
